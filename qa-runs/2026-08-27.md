## 1. The resolution writers (ISSUE-85 axis, T3)

`hypo-session-end.mjs` was driven with a payload on stdin against a transcript
placed under `<HOME>/.claude/projects/-qa-proj/<session-id>.jsonl`.

| payload            | result                                                           |
| ------------------ | ---------------------------------------------------------------- |
| `reason: "clear"`  | resolution written: `closedAtIndex: 3`, a real `closedPrefixSha` |
| `reason: "logout"` | no file created                                                  |

The recorded index matches the transcript's three records, which is the check
that matters: a writer that handed the stamp a decoded string instead of raw
bytes would have written nothing at all while still exiting 0.

## 2. The gate itself, deployed copy vs the copy users run today

The same four transcripts were fed to the deployed candidate and to the 1.7.2
copy in the plugin cache, which is what an installed user is running right now.

| transcript                                 | 1.7.2   | candidate |
| ------------------------------------------ | ------- | --------- |
| close phrase, then a clarifying question   | `false` | `true`    |
| close phrase, then a retraction phrase     | `false` | `false`   |
| a close phrase inside a command invocation | `true`  | `false`   |
| a plain close phrase                       | `true`  | `true`    |

Two rows flip, and they are the two the branch targets.

Row 1 is the friction this whole spec exists for: under 1.7.2 the approval
expires the moment the close procedure asks its own clarifying question, so a
close that needs one question needs the user to re-authorize it. Row 3 is the
provenance hole: a model-issued skill call lands as the same record shape a
human's typed slash command does, so the old gate opened on it.

Rows 2 and 4 are unchanged, which is the part worth stating explicitly. The fix
did not buy row 1 by weakening the retraction path or by making a plain close
stop working.

## 3. What this run does not cover

The read side is not wired yet (that is the next task), so no scenario here
exercises `readResolution` through a hook. The store is written and never read.
Everything in section 1 therefore proves the writers run in a deployed layout,
not that the recorded resolution changes any decision, because as of this branch
it does not.

A full `--apply-session-close` against the isolated vault was not run. Section 1
covers the `/clear` writer end to end in the deployed copy; the apply writer is
covered by the unit suite, including the case where a commit failure withholds
the marker and the resolution is still recorded.
