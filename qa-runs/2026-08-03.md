# QA run 2026-08-03: sync-status visibility (PR #225) + session-close artifact detection (PR #226)

Both PRs changed a hook and shipped with "Manual verification: not yet done" in their
bodies. #225 needed a live two-machine conflict, which its own body records as not
induced. #226 needed proof that the deployed copy of `hooks/hypo-shared.mjs` under
`~/.claude/hooks/` still loads, since that is the file real installs read.

Method follows the 2026-07-21 precedent: no deployment to the developer's real
`~/.claude`. Each PR's branch was exercised from its own worktree against a sandbox
`HOME`, with `scripts/init.mjs` run inside that sandbox so the hooks were genuinely
deployed the way an install deploys them. Every child process ran with `HOME` pinned
to the sandbox, so nothing touched the real config directory or the real vault.

Harnesses: `scratchpad/qa225.mjs`, `scratchpad/qa226.mjs` (sandboxes removed after
the run). Branches were tested as they stand on the PR; neither had been brought up
to `origin/main` (#225 was missing #224 and #227, #226 was missing #227, none of
which touch these code paths).

## PR #225: conflict-unresolved guidance and sync history

Worktree `feat/sync-status-visibility`. 19 checks, 19 PASS.

### Inducing a real conflict-unresolved

The PR's open item was that the state had only ever been written by hand into
`sync-state.json`. This run produced it through the real code path instead.

A bare remote, the sandbox vault as machine A, and a second clone as machine B.
B committed a `hot.md` edit and pushed; A committed a conflicting edit to the same
file. `syncRemote()` was then called from the **deployed** `hypo-shared.mjs` with a
`git` shim first on `PATH` that fails any invocation containing `--abort` and passes
everything else through to the real binary. That is the "filesystem/concurrent-mutation
edge" the function's own comment names, and it is the only way `merge --abort` fails
without corrupting the repository by hand.

Result: `.cache/sync-state.json` recorded `op: "conflict-unresolved"`, and
`git ls-files -u` still returned unmerged entries afterwards, so the tree really was
left half-merged. Both were asserted, not assumed.

### Session-start notice (deployed hook, real state)

- Exits 0, so the deployed hook loads and runs.
- Warns about a possibly half-merged tree and tells the user not to commit or push yet.
- Names the staging step. The literal text is `git -C <vault> add <resolved paths>`,
  so a search for `git add` does not match it; the first harness assertion was written
  that way and was wrong, not the code.
- Does not claim local work is "committed and safe".
- Does not fall through to the generic last-sync-failed line.

### doctor

- Gives the half-merged wording, names `git add`, and neither claims "committed and
  safe" nor advises `git pull --no-rebase`.
- With seven unresolved entries on file it lists five as
  `conflict-unresolved@<timestamp>` and appends `(+2 more)`. It does not echo each
  entry's error text, which is what the harness first looked for.
- Reports the last successful sync alongside the failure. The success record was
  produced by a genuine clean `syncRemote()` run rather than written by hand: the
  first attempt hand-wrote `{pull: "<iso>", push: "<iso>"}`, which is not the record
  shape, and doctor correctly answered
  `.cache/sync-last-success.json is invalid or unreadable — inspect manually`
  instead of silently ignoring it. That is worth keeping as an observation: a
  malformed success record is surfaced, not swallowed.

## PR #226: session-close artifact detection

Worktree `fix/close-artifact-gate`. 16 checks, 16 PASS.

### The deployed copy loads (the PR's blocking item)

`scripts/init.mjs` deployed into the sandbox `~/.claude/hooks/`. The deployed
`hypo-shared.mjs` contains `detectSessionCloseArtifact` and imports cleanly on its own.
All **14** deployed hooks that import `./hypo-shared.mjs` were then run as child
processes with a hook JSON payload on stdin; none produced `ERR_MODULE_NOT_FOUND`,
`Cannot find module`, a `SyntaxError`, or a `ReferenceError`. The concern that
motivated the requirement does not materialize.

### Detection and scope

- A clean vault reports `No close artifacts found`.
- A project `session-state.md` carrying a closing heading, with no marker, is reported
  as `1 close artifact(s) with no session-closed marker covering their date and project
scope`.
- The check only warns: doctor's exit code is unchanged from the clean-vault run.
- A marker whose `projects` array names that project covers the artifact
  (`all covered by a session-closed marker`).
- A marker naming a different project does not cover it.
- A marker carrying only the legacy flat `project` field does not cover it, matching
  the runtime scope resolver's own refusal to trust that field uncorroborated.
- Root `hot.md` with a closing narrative is detected, and is covered by a marker with
  an empty `projects` array, since it is a universal close artifact.
- Root `session-state.md` is not covered even with a marker present, because the real
  close procedure never writes it.
- A commit subject reading `session: close the 14th session` is detected from the git
  log with no marker on file.

### The documented gap is real

The PR states that a `hot.md` rewritten into a closing narrative that never literally
says 마감 or 종료 is not caught. Confirmed: with such a `hot.md` committed, the only
artifact doctor reports is the earlier close-worded commit, and `hot.md` does not
appear among the artifacts. The gap is where the PR says it is.

## Harness bugs found (not product defects)

Four of the six initial failures were the harness, and they are recorded because each
one is a way a future QA could mis-report a healthy build as broken.

1. Searching for `git add` in the session-start banner, which renders as
   `git -C <vault> add <resolved paths>`.
2. Counting doctor's per-entry output by the injected error text, which doctor does
   not echo.
3. Hand-writing `sync-last-success.json` in the wrong shape.
4. Leaving a marker from a previous step on disk before asserting that root `hot.md`
   is _not_ covered, and asserting "no artifacts at all" after a close-worded commit
   had already entered history permanently.

A fifth was environmental: the sandbox `HOME` has no global git identity, so commits
exited 128 until `user.email` / `user.name` were set on the sandbox repository.

## Verdict

Both PRs pass their outstanding manual-verification requirement. No product defect
was found in either.
